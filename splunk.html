01 Lab Overview

What we are monitoring

We monitor the Windows machine itself — specifically its Windows Security Event Logs. These logs record every login attempt, account change, and privilege use on the OS. Splunk collects and searches these logs so you can detect attacks in real time.

ComponentWhat it does in this lab
Windows Security Event LogsThe source of truth — records every logon, failure, account change, and service install on the OS. This is what we monitor.
Splunk Universal ForwarderReads the Windows Event Log channels and ships every new event into Splunk in real time.
Splunk EnterpriseThe SIEM — indexes those logs, lets you search with SPL, create dashboards and fire alerts.
Kali Linux (WSL2)The attacker — runs brute force and exploitation tools that create detectable events on the Windows machine.

Section 03

03 Installation Instructions

Part A — Windows Machine
1Install Splunk Enterprise

Run the downloaded .msi file. Use these settings during installation:

  • Install path: C:\Program Files\Splunk
  • Admin username: admin
  • Password: choose one and remember it
  • Select "Local System" when asked how to run the service
  • Allow the installer to start Splunk as a Windows service

After installation, open your browser and navigate to:

Browser — open this URL
http://localhost:8000

Log in with admin and your password. Click through the licence screen.

Verify Splunk is running:

PowerShell — Run as Administrator
Get-Service Splunkd
✅
Expected result

Status should show Running. If Stopped, run: Start-Service Splunkd

2Enable Receiving Port 9997

Splunk must listen on port 9997 to accept data coming from the Universal Forwarder.

🖱️
In Splunk Web UI

Settings → Forwarding and Receiving → Configure Receiving → New Receiving Port → type 9997 → Save

3Create the "windows" Index

All logs will be stored in an index named windows. Create it now so the forwarder has somewhere to send data.

🖱️
In Splunk Web UI

Settings → Indexes → New Index → Index Name: windows → Max Size: 5000 MB → Save

4Install Splunk Universal Forwarder

Run the Universal Forwarder .msi installer. When asked during setup:

  • Receiving Indexer Hostname: 127.0.0.1
  • Port: 9997
  • Admin credentials: same as Splunk is fine
  • Complete the installation

Verify it is running:

PowerShell — Run as Administrator
Get-Service SplunkForwarder
5Create inputs.conf — Tell the Forwarder What to Collect

This file tells the forwarder which Windows Event Log channels to read. Open Notepad as Administrator (right-click Notepad → Run as administrator) and create a new file at this exact path:

File path — save the file here
C:\Program Files\SplunkUniversalForwarder\etc\system\local\inputs.conf

Paste this as the complete contents of the file, then save:

inputs.conf — full file contents (copy all)
# Security Events — logins, failures, privilege use, account changes
[WinEventLog://Security]
disabled = 0
index = windows
renderXml = true

# System Events — services installed, system errors
[WinEventLog://System]
disabled = 0
index = windows
renderXml = true

# Application Events
[WinEventLog://Application]
disabled = 0
index = windows
renderXml = true

Restart the forwarder to apply the configuration:

PowerShell — Run as Administrator
Restart-Service SplunkForwarder
✅
Verify data is flowing

Wait 60 seconds. Go to Splunk Web → Search & Reporting and run:

index=windows | head 20

Windows events should appear within 1–2 minutes. Also run: index=windows | stats count by sourcetype to see all channels coming in.

Part B — Attacker Machine (Kali WSL2)
6Install Attack Tools on Kali

Open your Kali WSL2 terminal and run:

Kali Linux — WSL2 Terminal
sudo apt update && sudo apt install -y nmap hydra
7Find Your Windows Host IP from Kali

Inside WSL2, your Windows machine has a separate internal IP address. You need this for every attack command.

Kali Linux — WSL2 Terminal
cat /etc/resolv.conf | grep nameserver

The IP shown (usually 172.x.x.x) is your Windows host from Kali's perspective. Write it down — every attack command uses this IP.

📝
This IP changes on every WSL2 restart

Re-run the command above if your attacks seem to fail after a reboot.

Section 04

04 Attack & Detect

Each exercise has two phases. Run the ATTACK commands first, then go to Splunk and run the DETECT queries to find what was generated. Replace 172.x.x.x in all Kali commands with your Windows host IP from Step 7.

EX-01 Brute Force — Password Spraying Detection
OBJECTIVE — Generate failed login events (EventID 4625) and detect the burst in Splunk
⚔ ATTACK — Run on Kali WSL2

Extract the rockyou wordlist first if not already done:

Kali Linux — WSL2 Terminal
sudo gunzip -k /usr/share/wordlists/rockyou.txt.gz 2>/dev/null; echo "ready"

Now run the brute force against the Windows machine:

Kali Linux — WSL2 Terminal
# Brute force SMB login — replace 172.x.x.x with your Windows host IP
hydra -l administrator -P /usr/share/wordlists/rockyou.txt smb://172.x.x.x -t 4 -V
💡
SMB not responding?

Try RDP instead: hydra -l administrator -P /usr/share/wordlists/rockyou.txt rdp://172.x.x.x -t 4 -V

Or lock Windows (Win+L) and type wrong passwords 10 times manually — this also generates EventID 4625.

🔍 DETECT — Splunk Search & Reporting
Splunk SPL — see all failed logins
index=windows EventCode=4625
| table _time, Account_Name, IpAddress, Logon_Type, Failure_Reason
| sort -_time
Splunk SPL — count failures by account and source IP
index=windows EventCode=4625
| stats count by Account_Name, IpAddress
| sort -count
Splunk SPL — plot the failure burst over time
index=windows EventCode=4625
| timechart count by Account_Name
Splunk SPL — correlation rule: 5+ failures in 5 minutes
index=windows EventCode=4625
| bucket _time span=5m
| stats count by _time, Account_Name, IpAddress
| where count >= 5
🔔 CREATE ALERT

Run the correlation rule above → Save As → Alert

Alert typeReal-time
Trigger conditionNumber of Results is greater than 0
ThrottleOnce every 15 minutes

EX-02 Successful Login After Brute Force
OBJECTIVE — Detect many failures (4625) followed by a successful login (4624) from the same source
⚔ ATTACK — Run on Windows

After running hydra in EX-01, log into Windows normally with the correct password. This creates EventID 4624 immediately after the burst of 4625 failures.

💡
What this simulates

A brute force that eventually succeeds — the attacker got in. Many 4625s followed by a 4624 from the same source is a critical indicator of compromise in any SOC.

🔍 DETECT — Splunk Search & Reporting
Splunk SPL — successful logins
index=windows EventCode=4624
| table _time, Account_Name, IpAddress, Logon_Type
| sort -_time
Splunk SPL — failures and successes side by side
index=windows (EventCode=4624 OR EventCode=4625)
| eval Event=if(EventCode="4624","SUCCESS","FAILURE")
| timechart count by Event
Splunk SPL — find IPs that had failures then a success
index=windows (EventCode=4624 OR EventCode=4625)
| eval Event=if(EventCode="4624","SUCCESS","FAILURE")
| stats count(eval(Event="FAILURE")) as failures,
        count(eval(Event="SUCCESS")) as successes by IpAddress
| where failures > 3 AND successes > 0
| sort -failures
EX-03 New User Account Created
OBJECTIVE — Simulate attacker creating a backdoor account. Detect EventID 4720 and 4732.
⚔ ATTACK — Run on Windows (PowerShell Admin)
PowerShell — Run as Administrator
# Create a backdoor user account
net user backdoor P@ssword123 /add

# Add that user to Administrators group — privilege escalation
net localgroup administrators backdoor /add
🔍 DETECT — Splunk Search & Reporting
Splunk SPL — detect new account creation (EventID 4720)
index=windows EventCode=4720
| table _time, TargetUserName, SubjectUserName, Computer
Splunk SPL — detect user added to Administrators (EventID 4732)
index=windows EventCode=4732
| table _time, MemberName, TargetUserName, SubjectUserName
Splunk SPL — both events combined in sequence
index=windows (EventCode=4720 OR EventCode=4732)
| eval Action=case(EventCode="4720","Account Created",EventCode="4732","Added to Admin Group")
| table _time, Action, TargetUserName, SubjectUserName, Computer
| sort _time
🧹 CLEANUP — Remove the test account after the exercise
PowerShell — Run as Administrator
net user backdoor /delete
EX-04 New Service Installed — Persistence
OBJECTIVE — Simulate malware installing a fake service. Detect EventID 7045.
⚔ ATTACK — Run on Windows (PowerShell Admin)
PowerShell — Run as Administrator
# Create a fake service — simulates malware establishing persistence
sc.exe create "WindowsUpdateHelper" binPath= "C:\Windows\Temp\update.exe" start= auto
🔍 DETECT — Splunk Search & Reporting
Splunk SPL — detect new service installs (EventID 7045)
index=windows EventCode=7045
| table _time, ServiceName, ServiceFileName, ServiceType, ServiceStartType, ServiceAccount
Splunk SPL — flag services with suspicious binary paths
index=windows EventCode=7045
| search ServiceFileName="*Temp*" OR ServiceFileName="*AppData*" OR ServiceFileName="*Downloads*"
| table _time, ServiceName, ServiceFileName
🧹 CLEANUP — Remove the test service
PowerShell — Run as Administrator
sc.exe delete "WindowsUpdateHelper"
EX-05 Log Clearing — Anti-Forensics
OBJECTIVE — Simulate an attacker wiping evidence. Detect EventID 1102 in Splunk.
🚨
Why this matters

Attackers clear Windows Event Logs to destroy evidence. Splunk has already indexed those events — but the clearing action itself (EventID 1102) becomes the new evidence. This should always trigger a P1 alert in any real SOC.

⚔ ATTACK — Run on Windows (PowerShell Admin)
PowerShell — Run as Administrator
# Clear the Security event log — generates EventID 1102
wevtutil cl Security

# Clear the System event log — generates EventID 104
wevtutil cl System
🔍 DETECT — Splunk Search & Reporting
Splunk SPL — detect log clearing
# EventID 1102 = Security log cleared   EventID 104 = System log cleared
index=windows (EventCode=1102 OR EventCode=104)
| table _time, EventCode, SubjectUserName, Computer
🔔 CREATE ALERT

Run the query above → Save As → Alert · Title: LOG_CLEARED_CRITICAL · Trigger when results > 0 · No throttle · Action: Add to Triggered Alerts → Save

EX-06 Build a Live SOC Dashboard
OBJECTIVE — Create a 5-panel real-time monitoring dashboard in Splunk

In Splunk Web: Dashboards → Create New Dashboard → Classic Dashboards → Name: SOC Monitor → Save

Add 5 panels via Add Panel → New from Search Query. Use each query below as a separate panel:

Panel 1 — Failed Login Timeline  (Visualization: Line Chart)
index=windows EventCode=4625 | timechart count span=1h
Panel 2 — Top Accounts with Login Failures  (Visualization: Bar Chart)
index=windows EventCode=4625
| stats count by Account_Name
| sort -count | head 10
Panel 3 — New Services Installed  (Visualization: Table)
index=windows EventCode=7045
| table _time, ServiceName, ServiceFileName, ServiceAccount
Panel 4 — New Accounts Created  (Visualization: Table)
index=windows (EventCode=4720 OR EventCode=4732)
| eval Action=case(EventCode="4720","Account Created",EventCode="4732","Added to Admin")
| table _time, Action, TargetUserName, SubjectUserName
Panel 5 — Total Log Volume Last 1hr  (Visualization: Area Chart)
index=windows earliest=-1h | timechart count by sourcetype span=10m
⏱️
Enable Auto-Refresh

After saving, click Edit → Set Auto Refresh → Every 60 seconds. The dashboard now updates live every minute.
